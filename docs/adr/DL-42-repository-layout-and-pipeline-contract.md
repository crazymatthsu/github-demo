## Context

The platform will span several repositories: the connector family, the Deephaven server, a configuration
repository for the promoted environments, and more projects later. The owner wants one set of GitHub
workflows, actions and CI scripts to serve all of them with the least customisation per repository:
variables externalised into configuration, and the manual workflows' drop-down options derived from that
configuration rather than hand-edited. Copying `.github/` and `scripts/ci/` into each repository is the
default failure mode — every copy drifts, and a pipeline fix becomes N pull requests.

Reuse across repositories only works when every repository looks the same to the pipeline. The pipeline
therefore needs a **contract**: directories and file names it may assume, Gradle task names it may call,
and a small manifest for what no convention can derive. Decided conventions already fix parts of it: one
Gradle monorepo per deliverable (DL-01), the hybrid release lines (DL-03), the config tree per
env / flow / app / instance with four layers (DL-06, DL-07, D5 §6.1), the inventory per flow (DL-39, DL-41),
the deployment record without a write-back (DL-40), the version computation from tags (DL-04).

## Decision

### 1. Three kinds of repository

| Repository | Holds | Versioned by |
|---|---|---|
| `<org>/platform-ci` | the reusable workflows (`_*.yml`), composite actions, `scripts/ci/`, `scripts/runtime/` (what ships to the boxes), the Gradle convention plugins (`build-logic`, published to the Maven repository), the library chart, the shared compose template, the thin-workflow templates and `render-workflows.sh`, the design documents and ADRs, the `gha-*` skills | tags `v<major>.<minor>.<patch>`; consumers pin the major (`@v1`) |
| `<org>/<project>` (one per release line, e.g. `deephaven-connectors`, `deephaven-server`) | the apps of that project as Gradle subprojects, their Dockerfiles, charts and compose overrides, the `config/` tree of the envs the project deploys itself (dev), the integration-test infrastructure, the repository's own docs | its own tags `vX.Y.Z` (DL-04) |
| `<org>/platform-config` | `config/` for the promoted envs (qa, uat, prod) of every project; `values.yaml` / `compose.env` carry tag **and** digest | pull requests only (DL-09, DL-21) |

One project per repository makes the version, the image namespace, the hotfix line and the `project`
drop-down implicit. A repository may still hold several apps released in lockstep. A monorepo holding
two release lines (the demo) declares two `projects` in its manifest.

### 2. Layout of a project repository

```
<project>/
├── platform.yml                       the manifest (§4)
├── settings.gradle.kts                pluginManagement: the convention plugins by version; includes apps/* and libs/*
├── build.gradle.kts  gradle.properties  gradle/ (wrapper, libs.versions.toml)
├── .github/
│   ├── workflows/                     thin and generated: pr.yml main.yml release.yml release-please.yml nightly.yml deploy.yml rollback.yml
│   ├── CODEOWNERS                     hand-written
│   └── affected-map.yml               generated from the layout (one glob per app)
├── docs/                              README, runbooks, docs/adr/ of this repository
├── apps/<AppName>/                    one Gradle subproject per deployable app (`apps_dir` in the manifest; the demo keeps deephaven-connectors/)
│   ├── build.gradle.kts               plugins { id("buildlogic.spring-boot-app") } and little else
│   ├── src/main/java  src/main/resources/application.yml       layer 1: jar defaults and the import list of the layers (D5 §6.1)
│   ├── src/test/java                  unit tests
│   ├── src/integrationTest/java       component integration tests against the compose stack — a Gradle source set beside
│   │                                  src/test/, never under src/main/ (Maven has no standard slot for integration tests)
│   ├── docker/Dockerfile              FROM the company runtime base image (DL-13, DL-28); nothing app-specific but the jar
│   ├── docker/docker-compose.yml      only when the app needs more than the shared template (an override)
│   └── helm/<AppName>/                a thin wrapper around the platform library chart
├── libs/<lib>/                        shared code (connectors-framework): built and published, never deployed
├── config/                            the config tree of the envs this repository deploys itself (dev); same shape as platform-config
│   ├── _common/<AppName>/application.yml                       layer 2
│   └── <env>/
│       ├── _common/application.yml                             layer 3
│       ├── known_hosts
│       └── <flow>/
│           ├── workflows-config.yml                            boxes, deploy policy, instance → box (DL-40, DL-41)
│           └── <AppName>/
│               ├── app-common/{application.yml, values.yaml, logback.xml, app.env}                   layer 4
│               └── <AppInstance>/{application.yml, values.yaml, compose.env, app.env, vault.env}     layer 5 + deploy-time env
├── test-infra/                        compose stacks and test data for the integration tests
└── scripts/                           app-specific helpers only (a custom smoke check); platform scripts are never copied here
```

Removed by this layout: the per-app `scripts/run-compose.sh` wrappers (the deployer calls
`<version>/scripts/run-compose.sh <AppName> <AppInstance> <command>`, DL-41 short form) and most per-app
compose templates (today's three are identical apart from `${APP_NAME}`; the template lives in
`platform-ci/scripts/runtime/` and an app ships `docker/docker-compose.yml` only as an override).

### 3. The deploy-time env files, each with one reader and an allow-list

| File | Read by | Holds | Never |
|---|---|---|---|
| `compose.env` | compose only | how to run the container: `IMAGE_REPO`, `IMAGE_TAG`, the identity `APP_*`, `*_HOST_PORT`, `MEM_LIMIT`, `LOGS_DIR`, `DATA_DIR` | anything the process reads |
| `app.env` | the process (`env_file:` into the container; `app-common/app.env` then `<AppInstance>/app.env`) | `JAVA_OPTS`, `TZ`, `LOG_LEVEL_ROOT` | a Spring property name — application configuration stays YAML (D5 R3) |
| `vault.env` | the Vault client or agent | `VAULT_ADDR`, `VAULT_NAMESPACE`, the auth method and role, secret mount paths | a token or secret-id — those come from the box (`~/shared/<project>/`) or the Vault agent (D2) |

Config-lint check 5 validates each file against its own allow-list; check 9 (secret scan) covers all three.

### 4. The manifest `platform.yml`

```yaml
platform: v1                      # the platform-ci major this repository follows
kind: app                         # app | config | library
registry: ghcr.io/<org>           # or artifactory.company.com/docker-dev-local
projects:                         # one entry per release line; a single-project repository has one
  - name: deephaven-connectors
    apps_dir: apps                # the demo monorepo: deephaven-connectors
    kinds: [compose, helm]
  - name: deephaven-server        # the demo only: an independent line in the same repository (DL-03)
    apps_dir: deephaven-server
    tag_prefix: deephaven-server/
dev_envs: [us-dev]                # envs this repository deploys itself; promoted envs live in platform-config
notify: "#platform-cash"
```

Everything else is derived, never declared twice: apps from `<apps_dir>/*/docker/Dockerfile`, libraries from
`libs/*`, envs, flows and instances from the `config/` directories, deploy policy and boxes from the flow's
`workflows-config.yml`, versions from git tags. A value that can be derived from the tree is not a manifest
key.

### 5. The contract — what the shared pipeline may assume of every repository

| The pipeline calls or expects | Provided by |
|---|---|
| Gradle tasks `build`, `test`, `integrationTest`, `configLint`, `printVersion`, `dockerBuild`, `dockerPush`, `publish`, with their outputs where the convention plugins put them | the convention plugins, applied by version — the task names are the contract between workflows and repositories |
| versions from git tags: `vX.Y.Z`, `<next>-rc.<n>` on `main`, `<next-patch>-rc.<n>` on `hotfix/**`, `pr-<n>-<sha7>`; one release line per project, `tag_prefix` for an independent line | `buildlogic.git-version` (DL-04, DL-05) |
| images `<registry>/<project>/<AppName>` with the tag set of D4 §6.2 | manifest `registry` and `projects[].name` |
| an app is `<apps_dir>/<AppName>/docker/Dockerfile`, optionally with `helm/<AppName>/` | convention |
| `config/<env>/<flow>/<AppName>/<AppInstance>/` with the four layers and the inventory per flow | convention (D5 §6.1, §6.6) |
| the branch model: `main`, `hotfix/<x.y>.x`, release pull requests by release-please on both | D9 §6.11, D4 §6.6 |
| GitHub Environments named like the envs; secrets `DEV_DEPLOY_SSH_KEY`, `DEV_KUBECONFIG`, the bump App id and key | repository settings checklist shipped by platform-ci |
| the `ci:full` label; CODEOWNERS on `config/*-qa/**` and `config/*-prod/**`; the ruleset on `main` and `hotfix/**` | repository settings checklist |

### 6. Thin, generated trigger workflows

Each repository's `.github/workflows/*.yml` is a few lines: triggers, `uses: <org>/platform-ci/.github/workflows/_<x>.yml@v1`,
`secrets: inherit`. `render-workflows.sh` in platform-ci generates them from the templates, the manifest and
the `config/` tree — including the `choice` lists of the manual `deploy` and `rollback` workflows (project,
env, flow), because GitHub drop-downs are static YAML and nothing else can fill them. A lint check in `pr.yml`
fails when a generated file is stale ("run render-workflows"); a `platform-sync` workflow opens the
regeneration pull request when platform-ci publishes a new version; Renovate bumps the `@v1` pins and the
plugin version.

### 7. How a repository consumes platform-ci

Reusable workflows and composite actions by reference (`@v1`); the Gradle convention plugins by version
from the Maven repository (`pluginManagement`), never as a copied `build-logic/`; `scripts/ci/` and
`scripts/runtime/` through a checkout of `platform-ci@v1` into `.platform/` by the reusable workflows — the
version directory on a box (DL-41) carries the runtime scripts from that checkout.

### 8. What legitimately differs per repository

`platform.yml` (a dozen lines), `CODEOWNERS`, the generated workflows, the app wrappers (Dockerfile, chart
wrapper, compose override), and the GitHub settings — rulesets, Environments, secrets — which no file can
set and platform-ci documents as a checklist (or applies through the API).

## Alternatives considered

- Copying `.github/` and `scripts/ci/` into every repository: fastest first day, N divergent copies by
  month three; a pipeline fix becomes a pull request per repository.
- One monorepo for everything: no contract needed, but approvals, CODEOWNERS and release cadence do not
  scale across teams, and DL-01 chose one monorepo per deliverable.
- Git submodules for the shared scripts: excluded by DL-01.
- Composite actions only (no reusable workflows): shares steps, not jobs — matrices, environments and
  concurrency would still be copied.
- Dynamic drop-downs: GitHub Actions has none; generation is the only way to keep them in sync.
- Organisation rulesets with a required workflow: complementary (it can enforce that the gate runs in
  every repository), not a substitute for the contract.

## Consequences

- `platform-ci` is created mostly by moving files that exist in this repository: `.github/workflows/_*.yml`,
  `.github/actions/`, `scripts/ci/`, `scripts/run-compose.sh`, `scripts/smoke.sh`, `scripts/pool-deploy.sh`,
  `build-logic/` (then published), the skills and the docs; `render-workflows.sh` and the templates are new.
- The demo monorepo satisfies the contract without a split: `platform.yml` with two `projects`
  (`apps_dir: deephaven-connectors` and `deephaven-server`), the existing `config/` tree, the thin
  workflows generated in place of the hand-written ones; the per-app wrappers and duplicate templates retire
  with DL-41.
- `app.env` and `vault.env` extend config-lint check 5 with per-file allow-lists; `compose.env` loses the
  process variables (`JAVA_OPTS`, `TZ`, `LOG_LEVEL_ROOT`) to `app.env`.
- `platform-config` runs config-lint against published artefacts (the apps' configuration metadata and
  charts at the versions the tree names), not against a source checkout.
- A new project repository starts from the template (`platform.yml`, generated workflows, the settings
  checklist) and is pipeline-complete once CODEOWNERS and the GitHub settings are in place.
- A platform-ci major bump is a migration with notes; the reusable workflows assert the manifest's
  `platform` version and fail with a pointer to the notes when it does not match.
- To revise with the implementation: D1 §2.3 / §2.4 and §6 (layout), D7 (thin workflows, generation,
  the `platform-ci` reference), D5 §6.3 (the three env files, check 5), the `gha-pipeline-design` skill
  (a repository-layout reference and the generator), TODO.md §2.3 / §2.4.
